# イラスト違いの段2 — 記録・購入候補・買取・メルカリを絵ごとに分ける（設計案・2026-10-30）

状態: **10-30 ユーザーが案B を選択。段2a-1（別表を書き始めるだけ）を branch feat/art-stage2a で実装中**

## 0. 要点
- いまは検索結果だけが絵（元のイラスト／イラスト違い／漫画／GREEN／言語版）を分けている。価格の記録・購入候補・買取の最高額・メルカリは、カード×レアリティ×店の単位で絵が混ざる。
- 推奨は **案B「本表はそのまま・絵の内訳を小さな別表に」**。本表（price_history_v2 など）を読む口は約13のモジュールと5つの DB 関数があり、本表の形を変えると全部に手が入る。別表なら、絵を選べる画面の4つの口だけを直せば済む。
- 容量の見積もり: 別表3つで最大でも +約23MB（いま 379MB／無料枠 500MB）。

## 1. 現行の仕組み（2026-10-30 にコードと本番 DB で確認）
- 絵の印は `app._build_done` の中で `art_variant.annotate(results, card_name)` が付ける。**付けるのは画面に返す複製だけ**。記録の裏スレッド `_persist_scrape_async` には印の無い行が渡る。
- `annotate` は1枚のカードの**全店の行**を見て判定する。`_alt_only_codes` は「カーナベルが (イラスト違い) と書いた型番」を全店にそろえるので、1店だけの行では判定が弱くなる（カードラボのカタログ巡回は1店だけの行を書いている）。
- 記録の書き込み:
  - 販売: `price_persist.build_min_price_rows` → RPC `upsert_price_rows` → `price_history_v2`。キーは (card_id, shop_id, rarity_id, recorded_at)。中身は min_price・min_price_any・code・url。
  - 30日を過ぎた行は `rollup_price_daily` で `price_daily_min`（card×rarity×日の全店最安・100日保持）へ畳む。
  - 買取: `collect_buyback.collect_and_save_buyback` が店×レアリティの最高額を `buyback_history` へ（30日保持）。未開封は 10-28 から外している。
- **絵だけでなく言語版も混ざっている**: `build_min_price_rows` は `edition`（アジア版など）を見ないので、日本版のグラフにアジア版の安値が入りうる（死者蘇生の 25thシークレットのアジア版3件など）。
- 混ざり方を実データで数えた結果: price_history_v2 の約100万行のうち **7,529行（0.75%）は最安の型番が art_prints.json の「型番ごと違う絵」**。つまりその日のその店の「最安」は違う絵の値段だった。型番の中に絵が2つある灰流うらら PAC1 のような版は型番では見分けられないので、実際の混ざりはこれより多い。
- 読み出しの口:
  - 価格推移: `/api/price-history`（price_history 30日＋price_daily 100日）→ `static/js/price-trend.js`。`setView({rarity})` に絵は無い
  - 購入候補: `/api/wish-prices`・`/api/wish-shop-totals`（price_history 直近7日の店×レアリティの最新の値）。購入候補の1件は `{name, qty, rarity}` で、端末間同期（sync.py）にも同じ形で保存している。値下がり通知 `notify.py` も price_history
  - 買取の欄: `/api/buyback` のライブの行。**絵の印は付けていない**（`sealed` だけ）。最高額は `index-main.js` の `_renderBuyInline` が店ごとに出す
  - メルカリ: `mercari.aggregate` が出品名からレアリティを判定するだけ。DB には書かない（15分のキャッシュだけ）
  - 本表のその他の読み手（絵は選ばない）: 値動きランキング・X 投稿（x_poster・staple_post）・トップ（top_page）・パックの表（featured_matrix/featured_pack）・aggregations・chart_renderer・check_collection・shop_status。DB 関数は get_card_best_prices_json・movers 系3つ・rollup_price_daily
- 買取の商品名にも絵の言葉はあるが、販売とは書き方が違う（本番 API の灰流うららで確認）: カードラッシュは「[新]灰流うらら(座り)」（頭に [新]）。トレコロは「[両手閉じてる]」「[両腕開き]」で、型番が空。遊々亭・カードラボ・カーナベルは販売と同じ「(イラスト違い版)」「(通常イラスト)」など。今の `classify` をそのまま買取に当てると、カードラッシュとトレコロの行は判別できない。

## 2. 案

### 案A: 本表に「絵」の欄を足す
- 何を: price_history_v2・price_daily_min・buyback_history のキーに art_id（rarity_dim と同じ番号の辞書 art_dim）を足す。1行＝カード×店×レアリティ×絵×日。
- 過去の記録: art_id＝「区別なし」の番号で残す。グラフは切り替え日より前を「すべての絵」として描く。
- 容量: 増える行は案B とほぼ同じ（+約20MB）。ただし約100万行の表のキーを作り直す間、索引がもう1つ分（数十MB）一時的に要る。
- 直す口: **本表を読む全部**（Python 約13モジュール・DB 関数5つ・rollup）。絵を気にしない口も「どの絵の行を読むか」を決めないと、1日1行のつもりで2〜3行を読んで最安や値動きがずれる。MANGA の件（10-30）で、読み出しで寄せる案A が reviewer に6か所の漏れを指摘されて取りやめた形と同じ危うさがある。
- 段階: DB の作り直しと全部の読み手の修正を1回で出す必要がある（途中で止めると読み手が二重に数える）。

### 案B（推奨）: 本表はそのまま・絵の内訳を別表に
- 何を:
  - 記録の前に `annotate` を通す。夜の収集 `collect_and_save` は compare_prices の全店の行があるのでそのまま当てられる。検索の即時の記録 `_persist_scrape_async` も同じ行で当てる。
  - **本表（price_history_v2・buyback_history）は「代表の絵」の値にする**。そのレアリティに日本版の元のイラストか判別できない行があればその最安。無ければ日本版の違う絵（三戦の号のスーパーのように違う絵しか無いレアリティ）。それも無ければ言語版。レアリティが本表から消えないので、購入候補のレアリティの選択肢などはそのまま出る（10-28 に言語版のレアリティ名を変えて他の機能が空になった件の再発を防ぐ）。
  - **別表 price_history_art**（card_id, shop_id, rarity_id, art_id, recorded_at, min_price, min_price_any, code, url）に、**絵が2種類以上ある店×レアリティのときだけ**、絵ごとの値を全部書く（元の絵も含む）。30日を過ぎたら price_daily_art（card×rarity×art×日の全店最安・100日）へ畳む。買取も buyback_art（30日）。
- 過去の記録: 本表は手を付けない（絵の区別が無いまま）。別表は切り替え日から始まる。絵を選んだときのグラフは、切り替え日より前を「すべての絵（区別なし）」の薄い線で描くか、描かない（画面の案は段2b で決める）。
  - 任意: 本表の過去30日のうち、最安の型番が「型番ごと違う絵」の7,529行は、別表に移して本表から外す直しができる（code を手がかりにする。型番の中に絵が2つある版は直せない）。値動きの比べ方が切り替え日の前後で変わるので、値動きランキングは 10-28 の未開封のとき（`_BUYBACK_SEALED_EXCLUDED_FROM`）と同じく切り替え日より前と比べない。
- 容量（実データから見積もり）:
  - 本表の1日の行数は 2.3〜3.6万。そのうち絵の違いが分かっているカード107枚（art_prints.json の98枚＋カードラッシュの言葉の表）が 1,068〜1,757行（約5%）。
  - 死者蘇生の本番の検索結果では、店×レアリティ42組のうち絵が2群以上ある組が絵ごとに24行になった（カードの行の約57%）。
  - 107枚以外のカード・言語版の分も見込んで、多めに **販売の別表は1日2,000行**とすると、30日で6万行×約220B（本表の実測）＝**約13MB**。日ごとの別表は 500行/日×100日×約130B＝**約6MB**。買取の別表は 300行/日×30日×約380B＝**約3.5MB**。合わせて **+約23MB**（379MB → 約402MB・無料枠の80%）。
- 直す口:
  - 記録: price_persist（行の組み立て・別表の RPC）・collect_prices（夜の収集・カードラボのカタログ巡回）・app._persist_scrape_async・collect_buyback・rollup に別表の畳み込み・新しい SQL（表3つ・RPC 2つ・RLS 有効）
  - 画面: `/api/price-history` に `art` を足す・price-trend.js の setView に絵・購入候補の1件に `art` を足す（同期と古い端末は「art が無い＝代表の絵」で読む）・wish-shop-totals／wish-prices／notify は art があるときだけ別表を読む・買取の欄
  - 触らない: 値動き・X 投稿・トップ・パックの表・DB 関数（本表の中身が「代表の絵」に変わるだけ）
- 段階:
  - 段2a 記録を分ける（画面は変えない）。本表は代表の絵、別表に内訳。値動きの切り替え日の扱い。ここで本表のグラフの混ざりが減る
    - 10-30 実装時に2つに分けた: **段2a-1** 別表を書き始めるだけ（本表の中身は変えない）→ **段2a-2** 別表がたまってから、
      別表のある日の本表の行を「代表の絵」の値に書き直して切り替える。いきなり切り替えると、違う絵・言語版のほうが安かった組で
      値が段差になり、値動きランキング・X 投稿に偽の値上がりが出るため（値動きが読む30日分そろうのが目安）
  - 段2b 価格推移のグラフ（検索画面で選んでいる絵の線）
  - 段2c 購入候補（「この絵を購入候補へ」・どこで買うと安いかを絵ごと）
  - 段2d 買取の欄（買取の言葉の表を足して最高額を絵ごと。記録の buyback_art は段2a で一緒に書く）
  - 段2e メルカリ（下の案C と同じ、読み出しだけ）

### 案C: 記録は変えず、読み出しで分ける
- 何を: DB は触らない。検索画面ですでに持っている絵の印つきの行（ライブの検索結果）を使う。
  - 買取の欄・メルカリ: ライブの行に印を付けて、絵ごとの最高額・相場を出す（どちらも DB を使わないのでこれで足りる）
  - 購入候補: 「どこで買うと安いか」は7日分の DB を読むので、絵を指定した候補だけライブ検索の結果のキャッシュから引く（キャッシュが無ければ「すべての絵」の値に戻し、そう表示する）
  - 価格推移: **分けられない**（過去も今後も記録が混ざったまま）
- 容量: 増えない。
- 直す口: 買取の欄・メルカリ・購入候補の3つ。グラフは「すべての絵の最安」と注記するだけ。
- 弱点: 頼まれた4つのうちグラフが残る。購入候補はキャッシュ頼みで、まとめて買う計算が古い・欠けた値になりうる。

### 比べると
- 案A: 記録は一番素直だが、絵を選ばない口まで全部直す。一度に出す必要があり、漏れたときの害（最安・値動きのずれ）が広い。
- 案B: 本表を読む口は今のまま動き、中身が「代表の絵」になって良くなる。絵を選ぶ4つの口だけ直す。容量は +約23MB。段ごとに出せる。
- 案C: いちばん安いが、グラフは分けられない。買取の欄とメルカリだけなら十分。
- **推奨は案B**。理由: 4つすべてを分けられる中で、直す口が最も少なく、段ごとに出して戻せる。本表の「最安」が違う絵・言語版に引っぱられる今の混ざり（0.75%以上）も、画面に手を入れる前の段2a だけで減る。採らなかった案A は直す口の多さ、案C はグラフを分けられないのが理由。

## 3. あわせて決めること

### 3-1. 死者蘇生 2017-JPP03（海外版の絵なのに元のイラストと判定）
- 原因（Yugipedia の原文で確認）: Monster Reborn の image 欄は「1＝LART-EN／1.1＝L5DD-EN／2＝LPST-JP／2.1＝RA05-EN／3＝26LP-EN」で、2017-JPP03（2017年の世界大会の参加賞）はどの絵の代表にも出てこない。画像一覧（Card Gallery）でも 2017-JPP03 に絵の番号や AA が付いていない。カードラッシュも無印。どの手がかりにも引っかからないので、商品名に言葉の無い行は「元のイラスト」になる（`_BASE_WORDS` に空文字を含むため）。
- 案:
  - **推奨: 手で足す補正の表**（data/art_overrides.json。カード名→型番→元／違う・何番目の絵）。build_art_prints.py が表を作るときに足す。画像で確かめた型番だけを載せる。いまの対象は1件。
  - 採らない案: Yugipedia の画像一覧の各版の画像を、絵ごとの代表の画像と見比べて自動で判定する（画像の似ている度合い）。週1回の取得が重く、似た絵（日本版と海外版の死者蘇生は同じ構図）で外しやすい。補正の表が10件を超えるようなら考え直す。
- 未検証: 2017-JPP03 が Yugipedia の何番目の絵か（2 か 3 か）は、画像を見比べて決める必要がある。

### 3-2. 絵が3種類以上のカード（いまは元以外を「イラスト違い」にまとめている）
- 例: 青眼の白龍は KC01 と YAP1 が同じ「イラスト違い」。I：Pマスカレーナは PAC1 の違う絵と LOCH の新しい絵が同じ「イラスト違い」。
- 推奨: art_prints.json に**型番ごとの絵の番号**（Yugipedia の image 欄の番号）を持たせ、型番ごと違う絵の版は番号で分ける。build_art_prints.py は今も番号を読んでいるので、出力の形を `[型番…]` から `{型番: 番号}` に変えるだけ。番号の無い手がかり（店の言葉だけの「イラスト違い」）は、絵が2種類のカードなら2番、3種類以上のカードでは「違う絵（どれか不明）」として「すべての絵」にだけ出す。
- 段2a の記録はこの番号で分けて書く（あとから番号を足すと別表の過去が混ざるので、記録を始める前に決めたい）。
- **ユーザーに決めてほしいこと**: 画面での呼び方。案は「イラスト違い②（KC01 など）」のように番号と代表の型番を添える形。ほかに「海外版イラスト」「新イラスト」のような店の言葉を使う形もあるが、カードごとに言葉がそろわない。

### 3-3. 段2a の前に決めること・確かめること
- 判別できない行（art が空）は本表では元の絵の側に入れる（今の検索画面の既定と同じ「絞らない」扱い）。別表では「判別できない」として別に持つ。
- カードラボのカタログ巡回は1店だけの行なので、カーナベル頼みの型番の判定が効かない。art_prints.json の表で足りるか、同じ日の他店の行と合わせてから当てるかは、段2a で実データで比べる（未検証）。
- `_persist_scrape_async` に渡る行が全店そろっているか（キャッシュの店と取り直した店が混ざる）は未確認。

## 4. 未検証の前提
- 別表の行数（1日2,000行）は、絵の違いが分かっている107枚の行数と死者蘇生1枚の割合から多めに置いた値。107枚以外にどれだけ絵の違いがあるか、言語版の行がどれだけあるかは数えていない。段2a を入れたあと1週間の実測で確かめる。
- 買取の言葉（カードラッシュの「[新]…(座り)」・トレコロの「[両手閉じてる]」など）は灰流うらら1枚で見ただけ。段2d の前に人気カードで集め直す。
