作成日: 2026-08-09
最終更新: 2026-08-09（第2版）
状態: **設計レビュー待ち（未実装）**

**改訂履歴**

- **第2版: 白紙レビューを受けて「番号札方式（リビジョン制御）」に全面変更。** 第1版は単一端末でも「削除したカードが復活する」「レアリティ変更で行が2重になる」が発生する設計不備を含んでいた（後述 §12）

## 0. 平易な要約

**何をするか**
いまスマホとPCで別々になっている「購入候補」と「保存デッキ」を、両方の端末で同じ内容にする。

**なぜ**
テスト利用時に、PCで入れた購入候補がスマホで見られず不便だったため。ログイン（会員登録）は作らない。

**どうやるか**
サーバーがリストに**番号札**（1, 2, 3…）を振る。端末は「自分が知っている番号」を添えてデータを送る。

- 番号が合っていれば → そのまま上書き（＝他の端末は何もしていない）
- 番号がずれていれば → **両方を合体**して新しい番号を振る（＝他の端末が先に更新していた）

端末を増やしたいときだけ、片方の画面にQRコードを出してもう片方で読む。ユーザーがやる操作はこの**1回だけ**。

**影響**
- ユーザーから見た画面の操作は今と変わらない（同期は裏で動く）
- 新しいテーブルが2つ増える
- ネットが繋がらなくても今まで通り使える（後述の「ローカル優先」）

**次にやること**
この文書の承認 → 実装（3段階）→ 2端末での実機確認 → デプロイ

## 1. 決定事項

| 項目 | 決定 |
|---|---|
| 認証方式 | 会員登録なし。匿名の識別子（`sync_id`）をサーバーが発行 |
| 端末を紐づける操作 | ワンタイムリンク＋QRコード（入力欄なし・確認画面あり） |
| 競合の解決 | 和集合マージ（どちらのデータも消さない） |
| 同期対象 | 購入候補（wishlist）＋ 保存デッキ（mydeck）の両方 |
| 同期方式 | **リスト単位のリビジョン制御**（番号札方式） |

**採用しなかった案と理由**

- **メールログイン（アカウント制）**: 個人情報を預かる責任が発生し、実験的にDBを作り直せなくなる。まだ壊しながら作る段階のため見送り。将来 `sync_id` にメールを後付けする形で会員化できる設計にしてある（データ移行不要）
- **エクスポート／インポート**: 手動コピーであり、追加のたびに手作業が要る
- **要素ごとのマージ＋削除記録（第1版）**: オフライン並行編集を無損失で解決できるが、そのために削除記録・時刻補正・2種類のマージ規則が必要になり、実装量とバグ密度が数倍になる。利用者が1〜数名の段階では割に合わない

## 2. 設計の基本方針

### 2.1 ローカル優先（Local-first）

**`localStorage` を常に正とし、サーバーはミラー（複製）＋合流点として使う。**

- 画面の表示・更新は今まで通り `localStorage` を読み書きする
- サーバーへの送信は裏で非同期に行い、**失敗しても画面には影響させない**
- ネットワーク不通・DB停止時も、現状と完全に同じ体験が維持される

### 2.2 番号札方式（リビジョン制御）

購入候補と保存デッキそれぞれに、サーバーが単調増加のリビジョン番号を持つ。

- 端末は最後に受け取ったリビジョン（`base_rev`）を覚えておく
- 送信時に `base_rev` を添える
- サーバーは **「リビジョンが `base_rev` と一致する場合のみ書き換える」** という条件付き更新を1回のSQLで行う
  - **一致した** → クライアントの内容をそのまま採用し、リビジョンを+1する（通常経路。マージ処理は走らない）
  - **一致しない** → 他の端末が先に更新している。サーバーが**和集合マージ**を行い、リビジョンを+1して結果をクライアントに返す

**この方式が第1版の問題を丸ごと消す理由**

| 第1版で必要だったもの | 第2版で不要になる理由 |
|---|---|
| 削除記録（tombstone） | 通常経路では「クライアントのリストが正」なので、削除はそのまま反映される |
| 端末の時計ずれ補正 | 新旧判定に時刻を使わない（サーバー採番の番号だけで判定） |
| 通常マージと初回統合の2規則 | 「和集合」1本。QRでの初回統合も競合時と同じ処理 |
| 排他制御の作り込み | 条件付き更新1文で原子的に解決（後述 §4.3） |
| クライアント側のマージ実装 | サーバーの返り値をそのまま採用する |

**代償（許容済み）**
2端末がほぼ同時に編集し、片方が削除していた場合、**そのカードが1回だけ復活することがある**。頻度は低く、画面から見えるし、消し直せば済む。**データが消える方向には倒れない。**

## 3. データモデル

### 3.1 テーブル `sync_accounts`

```sql
create table sync_accounts (
  sync_id       uuid primary key default gen_random_uuid(),
  wishlist      jsonb  not null default '[]'::jsonb,
  wishlist_rev  bigint not null default 0,
  decks         jsonb  not null default '[]'::jsonb,
  decks_rev     bigint not null default 0,
  created_at    timestamptz not null default now(),
  last_seen_at  timestamptz not null default now()
);

create index sync_accounts_last_seen_idx on sync_accounts (last_seen_at);

alter table sync_accounts enable row level security;
-- ポリシーは作成しない（バックエンドの service_role のみ通す）
```

購入候補とデッキで**リビジョンを分ける**。片方の編集がもう片方の競合を誘発しないため。

`sync_id` は UUIDv4（122ビットのランダム）。総当たりでの推測は現実的に不可能。

**`wishlist` の要素**（既存の localStorage 形式と完全に同一。追加フィールドなし）

```json
{ "name": "青眼の白龍", "rarity": "", "qty": 3 }
```

**`decks` の要素**（既存の localStorage 形式と完全に同一）

```json
{ "id": "d_1754700000000", "name": "青眼", "text": "...", "main": [...], "ex": [...],
  "updated": 1754700000000 }
```

> 既存のデータ形式に一切手を加えないのが第2版の要点。第1版が必要としていた `updated_at` / `deleted` の追加は不要になり、それに伴う既存関数の大改修（`wishGet` の射影を通ると消える問題）も発生しない。

### 3.2 テーブル `sync_link_tokens`

```sql
create table sync_link_tokens (
  token       text primary key,
  sync_id     uuid not null references sync_accounts(sync_id) on delete cascade,
  created_at  timestamptz not null default now(),
  expires_at  timestamptz not null,
  used_at     timestamptz
);

create index sync_link_tokens_expires_idx on sync_link_tokens (expires_at);

alter table sync_link_tokens enable row level security;
```

`token` は `secrets.token_urlsafe(32)`。**有効期限10分・1回使用で失効。**

### 3.3 `SUPABASE_KEY` の種別（確認済み: service_role）

**確認日: 2026-08-09。結論: service_role キー。**

根拠: `ygores_cache.sql` は4つのテーブルすべてで RLS を有効化しているが、**ポリシーを1つも作成していない**。それでも本番のバックエンドおよび GitHub Actions の各ワークフロー（同じ `SUPABASE_KEY` を使用）がこれらのテーブルを読み書きできている。anon キーであれば RLS により全行が遮断されるため、service_role キー（RLS をバイパスする）であると確定できる。

したがって新テーブルも「RLS 有効・ポリシーなし」で既存の慣行に揃えてよい。

> なおキーの実物はローカルの `.env` には無く、Render と GitHub Secrets のみに存在する（`.env` / `.env.example` に `SUPABASE_` で始まる変数の記載なし）。ローカル開発でDBを使う場合は別途設定が必要。

## 4. 同期プロトコル

### 4.1 クライアントが持つ状態

`localStorage` に1件追加する（既存のキーは変更しない）。

```js
// キー: 'cardprice_sync_state'
{ "sync_id": "uuid", "wishlist_rev": 12, "decks_rev": 3 }
```

### 4.2 送信（push）の流れ

1. `wishSave()` / `savedDecksSet()` が呼ばれる
2. **2秒のデバウンス**（連続操作をまとめる）
3. 直前に送った内容と同一ならスキップ（無変化時は送らない）
4. `POST /api/sync/push` に `{sync_id, kind, base_rev, items}` を送る
5. 応答が `applied` → `base_rev` を更新するだけ
6. 応答が `merged` → 返ってきたリストを **`wishSave()` / `savedDecksSet()` 経由で** 適用し（§7.4）、`base_rev` を更新する
7. 失敗（ネットワーク断・429・500）→ **画面には何もしない**。指数バックオフで最大3回まで再送し、それでも駄目なら次のページ読み込み時に解決する

### 4.3 サーバー側の条件付き更新（競合の防止）

**通常経路**（1回のSQL、ロック不要）

```sql
update sync_accounts
   set wishlist = :items, wishlist_rev = :base_rev + 1, last_seen_at = now()
 where sync_id = :sync_id and wishlist_rev = :base_rev
```

更新行数が 1 なら成功（`applied`）。0 なら競合が起きている。

**競合経路**

1. 現在の行を読む（`wishlist`, `wishlist_rev = current`）
2. 和集合マージ（§5）を実行
3. `where sync_id = :sync_id and wishlist_rev = :current` で条件付き更新
4. また 0 行なら 1 に戻る（**最大3回**。それでも駄目なら `{ok:false, reason:"conflict_retry_exceeded"}` を返す。クライアントは次回に持ち越す）

これにより gunicorn の複数スレッド・複数タブ・2端末同時アクセスでも、**後着の更新が先着を踏み潰すことがない**。

### 4.4 受信（pull）の流れ

`POST /api/sync/pull` に `{sync_id, wishlist_rev, decks_rev}` を送る。
サーバーは**リビジョンが一致するリストは中身を返さない**（`unchanged: true` のみ）。

これにより、通常のページ読み込みでは数十バイトの往復で済む。

## 5. 和集合マージ規則（1本のみ）

競合時とQR統合時の**両方で同じ関数**を使う。サーバー側にのみ実装する（クライアントには実装しない）。

### 5.1 購入候補

- キー: `[name, rarity]` の**タプル**（文字列連結はしない。名前に空白が含まれても衝突しないため）
- 同キーが両方にある → `qty` は**大きい方**を採用（上限99。既存 `wishSetRarity` の頭打ちに合わせる）
- 片方にしかない → そのまま採用
- 上限200件を超えたら、後から来た側を切り捨てず **400 エラーで拒否**する（§9）

### 5.2 保存デッキ

- キー: `id`
- 同キーが両方にある → `updated` が大きい方を採用
- `id` が違えば**両方残す**
- デッキ名が衝突した場合（別 `id` で同名）→ 後から来た方を `「<名前> (2)」` にリネームして両方残す
  - サーバーが確定した結果を全端末が受け取るため、リネームは永続する
- 上限50件を超えたら 400 エラーで拒否

> **既知の限界**: デッキの `updated` はクライアントの時計に由来する。端末の時計が大きくずれていると、競合時に古い方の編集が勝つことがある。影響は「まれな競合時にどちらのデッキ内容が残るか」に限られ、デッキが消えることはない。実験段階では許容する。

## 6. API仕様

すべて `POST`。既存の `_same_origin_ok()` によるCSRF対策と、レート制限を適用する。
**`sync_id` は URL に載せない**（GA4がクエリ文字列を外部送信するため）。必ずリクエストボディで送る。

### 6.1 `POST /api/sync/push`

```
入力: { sync_id, kind: "wishlist"|"decks", base_rev: 12, items: [...] }
出力(通常): { ok: true, status: "applied", rev: 13 }
出力(競合): { ok: true, status: "merged",  rev: 13, items: [...マージ結果...] }
出力(DB不通): { ok: false, reason: "db_unavailable" }  // HTTP 200。クライアントは無視して続行
```

### 6.2 `POST /api/sync/pull`

```
入力: { sync_id, wishlist_rev: 12, decks_rev: 3 }
出力: {
  ok: true,
  wishlist: { unchanged: true } | { rev: 15, items: [...] },
  decks:    { unchanged: true } | { rev: 4,  items: [...] }
}
```

### 6.3 `POST /api/sync/init`

`sync_id` を新規発行する（§8の遅延発行で使う）。

```
入力: { wishlist: [...], decks: [...] }   // 端末の現在の中身を初期値にする
出力: { ok: true, sync_id, wishlist_rev: 1, decks_rev: 1 }
```

### 6.4 `POST /api/sync/link/create`

```
入力: { sync_id }
出力: { ok: true, token, url: "https://.../sync?t=...", expires_in: 600 }
```

### 6.5 `POST /api/sync/link/preview`

**引き換え前に確認画面を出すための下見。副作用なし。**

```
入力: { token }
出力: { ok: true, remote: { wishlist_count: 12, decks_count: 3 }, expires_in: 480 }
失敗: { ok: false, reason: "expired"|"used"|"not_found" }
```

### 6.6 `POST /api/sync/link/redeem`

確認画面のボタンを押したときのみ呼ぶ。**ここで和集合マージ（§5）を実行する。**

```
入力: { token, wishlist: [...端末Bのローカル...], decks: [...], old_sync_id: uuid|null }
出力: { ok: true, sync_id, wishlist: {rev, items}, decks: {rev, items} }
```

- `token` は `update ... where used_at is null` の条件付き更新で消費する。**1行更新できた場合のみ**引き換え成立（同時に2端末が踏んでも二重処理しない）
- `old_sync_id` の行は**削除しない**（誤操作時に戻れる余地を残す）

### 6.7 `POST /api/sync/unlink`

```
入力: { sync_id }
出力: { ok: true, sync_id: "新しいuuid", wishlist_rev: 1, decks_rev: 1 }
```

この端末だけ切り離す。現在のデータを新しい `sync_id` に複製して返す。他の端末は影響を受けない。

> 「他の端末を全部切る」モードは**今回は作らない**。誤って分裂を起こすリスクの方が、リンク誤送信のリスクより高いと判断した。

### 6.8 共通仕様

- **未知の `sync_id`**: 「行が存在しないことが確定した」場合のみ新規発行し、応答に `reissued: true` を含める（UIに「同期が解除されました」と表示）。DBエラー・接続不能では**絶対に再発行しない**（`{ok:false, reason:"db_unavailable"}` を返す）
- **レート制限**: バケットのキーは `sync_id`（無ければIP）。同一Wi-Fi下の2端末が同じIPを共有するため、IP単位では検証時に自分で自分を弾く
  - `push` / `pull` / `redeem`: 5秒に1回
  - `link/create`: 10秒に1回
  - 閾値の根拠は未校正（`# TODO: calibrate from data`）
- **429 の応答形式**: 既存の `_consume_rate_limit()` は `{"error": ...}` を返す。クライアントは `ok` の有無ではなく**HTTPステータスで判定**し、429 は再送キューに入れる

## 7. 画面の導線

### 7.1 端末を増やすとき（端末A）

購入候補タブとマイデッキタブに「**他の端末でも見る**」ボタンを置く。押すと QRコードとリンクが載ったダイアログが出る（有効期限10分のカウントダウン付き）。

QRコード生成は外部CDNを使わず、軽量ライブラリを `static/` に同梱する。

### 7.2 リンクを開いたとき（端末B）— 確認画面を必ず挟む

`/sync?t=...` は **`index.html` とは別の最小テンプレート（`sync.html`）** で配信する。Google Analytics のタグを載せない（トークンがクエリ文字列としてGoogleに送信されるのを防ぐため）。`robots.txt` にも `Disallow: /sync` を追加する。

画面には**自動で統合せず**、以下を表示してボタンを待つ。

> **他の端末と同期しますか？**
> この端末の購入候補 8件・保存デッキ 2件 と、リンク元の端末の 12件・3件 を合わせます。
> どちらのデータも消えません。
> ⚠ このリンクの送り主が自分自身であることを確認してください。
> 　[ 同期する ]　[ やめる ]

押した後、統合結果（何件になったか）を表示する。

> この確認画面がないと、攻撃者が自分のリンクを踏ませることで被害者のデータを自分のアカウントに吸い上げられる（レビュー指摘 S5）。実害は限定的だが対策コストがほぼゼロのため入れる。

### 7.3 同期の状態表示

同期が有効な端末には、購入候補タブに控えめな表示を出す（「他の端末と同期中」＋解除リンク）。同期していない端末には何も出さない（今と同じ見た目）。

### 7.4 pull／merge 結果の適用経路

**受信したリストは必ず `wishSave()` / `savedDecksSet()` を通して適用する。** 直接 `localStorage` に書いてはいけない。

理由: `wishSave()` はタブのバッジ更新と `syncPushSubscription()`（プッシュ通知の対象カード更新）を呼んでいる。直書きするとこれらが更新されず、値下がり通知の対象がずれる。

適用中は送信フックを止めるフラグを立て、受信 → 保存 → 再送信の無限ループを防ぐ。

## 8. `sync_id` の遅延発行と、pull を走らせる範囲

**全ページが `index.html` を返す**（`/`, `/card/<name>`, `/buy/<name>`, `/featured` など7経路）。無条件に `sync_id` を発行すると、**検索流入した匿名の訪問者全員にDBの行ができる**。

したがって:

- **発行条件**: 購入候補または保存デッキが**1件以上ある**とき、または「他の端末でも見る」を押したとき。それまでは `/api/sync/init` を呼ばない
- **pull を走らせる場所**: `sync_id` を持つ端末が、トップページ・購入候補タブ・マイデッキタブを開いたとき。**カード個別ページの閲覧では走らせない**
- 既存利用者は購入候補やデッキを既に持っているので、初回アクセス時に自動で発行される（操作不要）

## 9. 上限とバリデーション

超過時は**切り捨てず 400 で拒否**する（サイレントなデータ消失を防ぐ）。クライアントはUIで警告する。

| 対象 | 上限 | 根拠 |
|---|---|---|
| 購入候補 | 200件 | 新規 |
| カード名 | 50文字 | 既存 `MAX_CARD_NAME_LEN` |
| 保存デッキ | 50件 | 新規 |
| デッキ `text` | 6,000文字 | 既存 `MAX_DECK_PARAM_CHARS` |
| デッキ `main`/`ex` の枚数 | 80枚 | 既存 `MAX_DECK_CARDS` |

## 10. 既存データの移行

1. 購入候補またはデッキが1件以上ある端末が、対象ページを開く
2. `cardprice_sync_state` が無ければ `/api/sync/init` を呼ぶ
3. サーバーが `sync_id` を発行し、送られたローカルデータをそのまま初期値として保存する
4. クライアントが `sync_id` と各リビジョンを `localStorage` に保存する

**ユーザーの操作は不要。既存データが消えることはない**（サーバー側が空なので、送った内容がそのまま初期値になる）。

## 11. 一人回しページの扱い（スコープに含む）

`static/solitaire/js/ui/event-handlers.js` と `deck-input-panel.js` が、同じ `cardprice_saved_decks` を **`savedDecksSet()` を経由せずに直接読み書きしている**。このままでは一人回しからのデッキ保存が同期されない。

対応: 同期クライアントを `static/shared/sync-client.js` として切り出し、`index.html` と一人回しの両方から使う（プロジェクトの CLAUDE.md「新機能のロジックは新規モジュール／static配下、`app.py`・`index.html` には配線だけ」に沿う）。

一人回し経由で保存されたデッキは `main`/`ex` を持たないため、サーバー側バリデーションでこれらを**必須にしない**。

## 12. セキュリティ・プライバシー

| 論点 | 対処 |
|---|---|
| `sync_id` の漏洩 | URLに載せない。POSTボディのみ。HTTPS前提 |
| トークンのGoogleへの送信 | `/sync` を GA タグのない専用テンプレートで配信＋`robots.txt` で除外 |
| 逆方向フィッシング | 引き換え前に件数付きの確認画面（§7.2） |
| リンクの誤送信 | 10分・1回限りで失効。`unlink` で事後的に切り離せる |
| CSRF | 既存の `_same_origin_ok()` を全エンドポイントに適用 |
| 総当たり | `token` 32バイト＋レート制限＋短命 |
| トークンの二重使用 | `where used_at is null` の条件付き更新 |
| DBの直接アクセス | 新テーブルは RLS 有効化。ポリシーは作らない |

**個人情報は保存しない。** 保存するのはカード名・デッキ内容・ランダムな識別子のみ。

**ただし、プライバシーポリシーの改定が必須。** 現行の掲載内容（`index.html` 1230行付近）は「収集する情報＝IPアドレス（永続保存しない）とCookie」となっており、今回の変更（購入候補・デッキ内容のサーバー保存、永続識別子の割り当て）は記載範囲を超える。P1 の完了条件に含める（`tests/test_privacy_policy.py` の更新も含む）。

## 13. 実装計画（3段階）

| 段階 | 内容 | 完了条件 |
|---|---|---|
| **P1** | DDL適用（RLS込み）＋ `init`/`push`/`pull` ＋ **購入候補**の同期＋遅延発行＋プライバシーポリシー改定 | 単一端末で購入候補の追加・削除・レアリティ変更が今まで通り動く。Supabase に行が作られ、リビジョンが増える。マージ関数の単体テストが通る |
| **P2** | **保存デッキ**の同期を追加（一人回しの2ファイル対応を含む） | デッキの保存・削除・上書き、一人回しからの保存が今まで通り動き、同期される |

**孤児データのGC（日次cron）は今回作らない。** 遅延発行（§8）により無駄な行がほとんど生まれないため、行数が3桁になってから検討する。

**テスト**

サーバー側の和集合マージ関数の単体テストを `tests/test_sync_merge.py` として追加する。最低限これらを検証する。

- 購入候補: 同キーの `qty` が大きい方になる／片方にしかない要素が残る／上限99で頭打ち／名前に空白があってもキーが衝突しない
- デッキ: `id` 一致は `updated` の新しい方／`id` 相違は両方残る／同名別idがリネームされる
- リビジョン: 条件付き更新が競合時に0行になり、リトライで解決する
- 上限超過が 400 で拒否される

2端末（PC＋スマホ）での手動E2E確認は P3 完了時に実施する。

**DDLの適用**: このプロジェクトの既存手順（Supabase管理API直叩き）に従う。

## 14. 既知のリスク・未決事項

1. **復旧不能性**: 両方の端末のブラウザデータを消すとデータは戻らない。匿名方式の本質的な弱点であり、承知の上で採用している。将来メール登録を任意で足せる設計にはしてある
2. **競合時に削除が1回巻き戻ることがある**（§2.2の代償）。データ消失方向には倒れない
3. **デッキ競合時の新旧判定はクライアント時計に依存**（§5.2の既知の限界）
4. **QRライブラリの追加**: 依存が1つ増える。選定は実装時に確認する
5. **`SUPABASE_KEY` の種別が未検証**（§3.3）。実装前に確認する
6. **ニューロン連携のChrome拡張が `localStorage` のデッキを直接書いているかどうか未確認**。書いているなら §11 と同じ対応がもう1経路必要（拡張本体はこのリポジトリ外）
7. **`push_subscriptions` との重複**: プッシュ通知は今も端末ごとに購入候補をサーバーへ送っている。同期導入後にこの2系統をどう整理するかは本設計の対象外（別タスク）。当面は両立して問題ない
8. **Supabase無料枠**: 書き込み頻度は抑える設計だが、実測は運用開始後に確認が必要
