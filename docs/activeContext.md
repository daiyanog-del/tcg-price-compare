## 2026-08-19: 同期の本番E2E通過・モバイル改善・分割プラン修正の引き取り

### 端末間同期 = 完成（本番で2端末E2E通過）
発行→確認画面→合流（購入候補・デッキとも和集合）→旧アカウント残存→トークン1回使い切り→解除、まで本番で確認。

**実機で初めて出た不具合（テストは全通過していた）**
1. レート制限バケットを背景同期と共有し、タブを開いた直後のpullが枠を食って「他の端末でも見る」がほぼ必ず429
2. その失敗が画面に何も出ない（背景同期の「失敗を出さない」規則をユーザー操作にも適用していた）

4. 初回登録の二重実行で孤児行ができる
5. **未連携なのに「他の端末と同期中」と誤表示**（ユーザー指摘。`sync_id` の有無で判定していた → 使用済みトークンの有無を見る `is_linked()` に変更）

### 購入候補リストのモバイル表示（ユーザー指摘「カード名がつぶれて見づらい」）
- 原因: 固定幅135pxのレアリティ選択と同じ行に並び、唯一の可変要素であるカード名が83pxまで潰されて省略されていた
- 対応: `@media(max-width:767px)` で3段グリッド化（名前は独立行・全幅）。高さ102px・320〜767pxで切れなし。タップ対象は擬似要素で**当たり判定のみ**44px相当に拡張（行の高さは不変）。レアリティのselectだけは `select::after` がヒットテストされないため未対応（31pxのまま・判断待ち）
- **教訓**: 合格条件を `scrollWidth <= clientWidth` に置いたのは誤り。折り返しを許可した時点で常に真になり、「幅89pxの列に3行折り返し」でも合格してしまった。**行数と枠幅で判定すべき**

### まとめ買い分割プランの修正を別セッションから引き取り
別セッション（最安店舗の組み合わせロジック／購入候補の割引計算）が実装・レビュー済みで未コミットだったものを本セッションでコミット・デプロイした。

### ★P2デプロイ直後にデータ消失バグを発見・即修正（2026-08-13・実ユーザー被害なし）

- **症状**: 購入候補がローカルにある状態でデッキを保存 → 次のpullで**購入候補が空になる**（本番ブラウザで再現）。逆方向も同じ
- **原因**: `_ensureAccount` が**きっかけになった種別のリストしか init に送らず**、もう一方を rev=0 で開始していた。設計文書 §6.3 の init は `{wishlist, decks}` の両方を受け取る仕様であり、**実装が設計から外れていた**。rev=0 のままpullが走るとサーバー側の空リストが「新しいデータ」として上書き適用される。「次のpushで自然に解決する」という実装コメントの理屈は**push経路でしか成り立たない**（pull経路を考慮していなかった）
- **被害なし**: 発覚時点で `sync_accounts` は0行＝まだ誰も同期を開始していなかった。露出はP2デプロイからの十数分のみ
- **修正**: ①initは常に両方のリストを送り両方のrevを保存 ②push再発行経路も同様 ③**救済ルール**=ローカルrevが0の種別はpull結果を適用せず、ローカル内容をpushして和集合マージで合流させる
- **テスト**: `tests/js/sync_client_data_loss_check.js`（実物のsync-client.jsをNodeで直接ロード）＋pytestラッパー。**修正前コードに当てると落ちること**まで確認済み（偽陰性でないことの裏取り）
- **残る軽微な穴**: 救済ルールは「rev=0 かつ ローカルも空」の種別を push しないため、その種別は永久にサーバーから受け取れない。該当するのは旧バグ期間に作られた端末のみで実在せず（0行）、実害なし
- **教訓**: 設計文書に書いた仕様（両方送る）から実装が外れており、レビューでも拾えなかった。**サーバー側の単体テストだけでは検出できない**（クライアントの状態遷移バグ）

## まとめ買い最安店舗に送料と最低注文金額を反映（2026-08-05）

- **何が抜けていたか**: 「まとめ買い最安店舗」は**商品代金の合計だけ**で並べており、送料と最低注文金額を見ていなかった。とくに**遊々亭は送料が常に無料**なので最安の位置に出やすいが、**商品代金1,000円未満は注文自体ができない**。カーナベルも2,000円未満は同じ。「¥0で1位なのに買えない」状態だった
- **最低注文金額があるのは2店だけ**（遊々亭1,000円・カーナベル2,000円）。残り4店は注文条件ページを2通りのパターンで走査しても金額の下限は無く、あるのは買い占め対策の**枚数**制限のみ
- **送料は一意に定まらない**（配送方法 × 厚さ（枚数） × 地域）。枚数から厚さを正確に出す手段が無いため、**各店で最も安い配送方法・最小の厚さ**で固定し「最低でもこれだけかかる」の下限見積もりとして扱う（ユーザーと合意）。UIフッターに前提と確認日を明記
- **カーナベルの送料無料条件だけ未確認**。検索上は「4,000円以上で無料」だが公式に記載が無く、推測を入れず「無料条件なし（常に100円）」で実装。TASKS.md に起票済み
- **送料ルールはAPIで配る**。画面は DB 相場で描画後、リアルタイム検索で合計が後から増えるため、無料しきい値をまたぐとフロントでも再計算が要る。Python と JS の二重管理を避けるため `shipping_rules` を応答に含めた
- **実装中に自分で入れた不整合をローカル実機で発見**: 1枚も揃わない店舗（商品代金0）に送料¥100と「最低注文金額まであと¥2,000」が付いていた。「金額が足りない」ではなく「買う物が無い」ので判定対象外に修正（テストも追加）
- **やらないと決めたこと**: 複数店に分けて買う組合せ最適化。各店の送料を単純加算した「1店舗でまとめ買いした場合」の比較に留める
