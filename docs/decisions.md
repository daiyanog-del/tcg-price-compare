## 2026-08-03: カードラボ403の原因特定（流量ベースの遮断）と safe_get の作法改善
- **決定**: `safe_get` に3点の対処を入れた（案A）。カードラボ固有の分岐は作らず、全店舗共通の取得関数として直した
  - **① 403（および429以外の4xx）は再試行しない**。従来は `retries=1` で403も再試行しており、遮断後の1,451件が実質約2,900リクエストになっていた
  - **② 全スレッドで `requests.Session` を共有**（`_get_session`）。従来は毎リクエストが新しい PHPSESSID を発行させ、1晩に数千個のセッションを店舗側に作らせていた。接続の再利用（keep-alive）も効く
  - **③ ホスト単位のサーキットブレーカ**。連続403が5回でそのホストへのリクエストを30分停止。TTLを設けたのは app.py が常駐プロセスで、恒久ブロックだとライブ検索が再起動まで復旧しないため。打ち切り中の空振りは `_note_fetch_error()` で取得失敗として数え、「0件＝在庫なし」と混同しない
- **原因（Renderログ3晩の実測）**: **恒久的なIPブロックではなく、一定量を超えたところで発動する流量ベースの遮断**
  - 8/1実行: 20:00:50Z開始 → **最初の403は21:32:26Z・1248/2717枚目**。それ以前は403ゼロ。以降は実行終了(23:23:45Z)まで100%失敗
  - 8/2実行: 21:32:29Z（ほぼ同位置）／8/3実行: 21:12:28Z・**1020/2719枚目**
  - **翌晩はまた最初から通る**＝時限式で自動解除。しきい値が1,020〜1,248と揺れるので固定カウントではなくレート併用の判定と思われる
  - カードラボ**買取**（c-labo-kaitori.jp、収集約300件）は403ゼロ。Web本体のライブ検索も403ゼロ＝**低流量なら通る**
- **カーナベル買取（2026-06-16）とは別種**。あちらはデータセンターIPの恒久ブロックでES APIへ逃げたが、今回は代替APIが存在しない
- **代替経路の調査結果**: サイト基盤は**おちゃのこネット（ocnk）**と特定（`res/touch003/js/pack/ocnk-min.js`）。Serverヘッダは Apache 単体でCDN/WAFベンダ無し＝遮断は origin 側
  - 公開JSON/内部APIは**無し**。`/rss/rss.php` は最新100件のみ、`/sitemap.xml` は応答が重くタイムアウト（かつ価格を持たない）
  - 使える公開パラメータ（実測）: `&num=120`（1ページ120件。`240`は無効で60に落ちる）／`&page=N`／`.item_count` 要素に総ヒット件数
  - **カテゴリ一括巡回（案C）は経路が未確定**。検索ファセットのID空間と閲覧可能カテゴリのID空間は別物で、ファセット由来のID（1140/1081/1277）は `/product-list/{id}` が404。一方 `/product-list/676?num=120` =「遊戯王OCG:効果」**7,415件**は閲覧可能。**遊戯王OCGの兄弟カテゴリID一覧を特定できていないため総コストは未確定**（`/page/40` の108グループは商品カテゴリ体系と一切重ならず、当初の見積りは誤りだった）
- **未検証の前提**: ②のセッション使い回しが遮断回避に効くかは未検証（効果ゼロの可能性あり）。しきい値の正体（件数かレートかバイト量か）も未特定
- **測定方法**: 専用の負荷テストは同じ迷惑を二重にかけ当日分のクォータを潰すため行わない。**本番実行の翌晩に「403が始まるカード番号」が 1248/1020 からどう動くかで観測**する
- **`num=120` は今回入れない**。レスポンスが1.7MB→2.0MBに増えて②の効果測定に交絡するため。ページ送り欠如は別タスクとして残す（1晩1変数）
- **検証**: pytest 222件全緑（新規 tests/test_safe_get.py 12件）。実機で販売41件・買取31件を取得し、PHPSESSID が1個だけ保持されることを確認

## 2026-08-03: 店舗検索の取りこぼし修正 第2弾（カードラッシュ）＋ページ送り追加
- **決定**:
  - **照合の区切り集合を `_FLEX_SEP_CHARS` 定数に集約**（従来は `_FLEX_SEP` と `_build_flex_pattern` の split に同じ集合が重複しており、片方だけ直すと壊れる状態だった）。実測で仕分けた記号を追加: `「」『』【】《》〈〉〔〕☆★“”’'〜～×@&!?./<>=~`
  - **ギリシャ文字（α β γ ζ Σ Ω）等の識別子は区切りにしない**。区切りにすると「磁石の戦士α」と「磁石の戦士β」が同一カード扱いになる
  - **カードラッシュ専用の検索語生成 `_cardrush_search_query()` を新設**し、販売・買取の2箇所に適用。他店は `_normalize_search_query` のまま（実測で他店は増減ゼロだったため影響を閉じた）
  - **カードラッシュ販売にページ送りを実装**（`max_pages=5`）。存在しないページは1ページ目が返るため、内容の重複で終端を検出する
  - **空パターンのガードを追加**。カード名が区切り記号だけ（例「☆」）だとパターンが空になり、空マッチが全位置で成立して記号始まりの商品名を拾ってしまう。ユーザー入力が `/api/search` に直接届くため防いだ
- **記号の仕分け根拠（実測）**: 判定基準は「店舗が商品名から落とすか否か」。カードラッシュ実データで確認し、落とす記号のみ区切りに入れた。`. = ~ < > & ! ? /` は master 15,522件の棚卸しでも別カードと衝突しないことを確認
- **ページ送りを追加した理由（reviewer指摘）**: 検索語から記号を落とすと母集団が広がり、1ページ100件の枠から正解商品が押し出される。「No.39 希望皇ホープ」で総件数200件・通過57→48件の**回帰を実測**していた。直そうとしたバグを別経路で再生産するところだった
- **ページ送りの影響は限定的**: ランダム30件のうち件数が増えたのは2件のみ（100件超は人気カードに限られる）。ただし灰流うらら 82→151件、青眼の白龍 51→240件と、人気カードでは大きく増える
- **検証**: pytest 210件全緑／実装コードそのものを使った総当たり（区切りを含む全カード **8,301件** × マスタ15,423件、reviewer指摘を受けて母集団を588件から拡大）で取りこぼし0件・過剰一致0件／実商品名1,356件×49カードでも GAINED 301件・**別カード混入0件・LOST 0件**／販売5店・買取4店の実データ比較でカードラッシュ以外は増減ゼロ
- **reviewerが検出した見落とし2件をマージ前に修正**: ①上記のページ送り ②`’`(U+2019) と `'`(U+0027) 未対応（「Evil★Twin’s トラブル・サニー」が0件のままだった → 27件）
- **既存バグとして別チケット化**（今回の回帰ではないが可視化した）: 末尾境界チェックが区切り集合と非同期（`nc in "・－-ー、,&"` の6文字ハードコード）／検索語の空白圧縮が他7経路に無い／カードラッシュ検索語でコロンが落ちない／買取moversにガード②が無い／トークン商品の混入。詳細は TASKS.md
- **X自動投稿は第1弾から停止継続**。第2弾でも高額カード11件中3件が急落閾値を超える（例: マジマジ☆マジシャンギャル 9,980→1,880円 -81.2%）。**再開は第2弾デプロイ日から3日以上あける**こと

## 2026-08-03: 店舗検索の取りこぼし修正 第1弾（トレコロCB・カーナベル）＋X投稿の一時停止
- **背景**: 「店舗にあるはずのカードが検索でヒットしない」（ユーザー報告: トレコロCB/カードラッシュ/カーナベル）。調査の結果、**3店とも原因は別物**だが構造は同じで、**TCGYM側が検索語や照合を正規化しすぎて店舗側の実表記と食い違い外している**ことが共通していた
- **決定（第1弾で実施）**:
  - **トレコロCB**: 検索語生成を `_torecolo_search_query()` に集約（販売 scrape_torecolo と買取 scrape_torecolo_buy にコピペされていた2箇所を統合）。処理は「ダッシュ類を全角ハイフン U+FF0D へ統一」のみに変更。旧実装の「NFKC半角化＋ダッシュ→スペース置換」を廃止
  - **カーナベル**: `_kanabell_wildcard_values()` を追加し、ESクエリの should に半角版と全角版の wildcard を両方入れる。販売 scrape_kanabell・買取 scrape_kanabell_buy・画像取得 kanabell_card_image_url の3箇所に適用
  - **X自動投稿を一時停止**（post-x.yml の schedule をコメントアウト、再開予定 2026-08-07）
- **実測で確定した事実（推定を3回外したため、すべて実機で裏を取った）**:
  - トレコロの検索がヒットする条件は**ダッシュが U+FF0D であることのみ**。英数字の全角/半角は無関係（`D－HERO …`=7件 と `Ｄ－ＨＥＲＯ …`=7件、`No.39 …`=50件 と `Ｎｏ．３９ …`=50件）。半角ハイフン U+002D・他のダッシュ異体・スペース置換はいずれも0件。**旧実装のスペース置換が不具合の原因そのもの**
  - トレコロに NFKC を通してはいけない。ローマ数字を Ⅹ のまま登録しているため X へ潰すと取りこぼす（アルカナフォースⅩⅩⅠ: 4件→13件）
  - カーナベルESの card_name は**半角格納と全角格納が混在**（全角英数を含むのは39,994件中32件＝14種類、うち12種類が追跡対象）。「カーナベルのESは半角で格納されている」という従来のコード内前提は誤りだった
  - 14種類のうち2種類は「Ｎｏ.１０４ …」のように**ピリオドだけ半角の混在表記**。このため全角版は**英数字のみ**を変換する（記号も全角化すると当該2種類が0件のまま＝reviewer指摘で発覚した実装バグ）
- **X投稿を止めた理由**: 修正でこれまで取得できなかった安い出品が新たに記録される。min_price は MIN 集計のため**下方向にしか動かず**、実際には値下がりしていないカードが「急落」として自動投稿される。高額カード32件の実測で**11件が急落閾値(-500円/-30%)を超過**（例: サイバー 680→10円 -98.5%、いたずら好きな双子悪魔 570→20円 -96.5%、ヘリオス・トリス・メギストス 2,080→780円 -62.5%）。**既存2ガードは今回効かない**（既存店舗の最安値低下なので共通店舗ガードを素通り、2店同時修正で複数店ガードも突破）。get_price_movers の比較窓が3日のため収集4回分を空ける
- **影響のない経路（確認済み）**: Web Push通知（notify.py）は Render Cron 移行時に呼び出しが外れており現在停止中。買取ランキングは外部発信しない
- **根拠**: pytest 184件全緑（新規 tests/test_search_query.py 18件）、トレコロは実機で確認（デスドグマガイ0→4件、灰流うらら53件で不変）、カーナベルはESへ直接問い合わせて確認（取りこぼし救済・既存件数不変）、reviewer監査1巡（重大指摘3件をすべて反映）
- **残件（第2弾）**: カードラッシュの照合修正。実測で記号を仕分け済み（区切り扱い=「」『』☆★“”〜～＠＆！．／×／文字扱い=ギリシャ文字）。この方式でカード名15,423件の総当たり検証は取りこぼし0件・過剰一致0件。カードラッシュのみ検索語の記号除去も併せて必要（販売176→289件、買取79→109件）

## 2026-06-04〜06-11: gunicorn 2ワーカー×4スレッド → 1ワーカー×8スレッド + MALLOC_ARENA_MAX=2
- **決定**:
  1. （2026-06-04, 3ebe885）gunicornの起動オプションを `--workers 2 --threads 4` から `--workers 1 --threads 8` に変更
  2. （2026-06-11, 60d3239）Dockerfileに環境変数 `MALLOC_ARENA_MAX=2` を追加
- **理由**:
  1. Render無料プランはCPUが0.1コア相当であり、worker=2にしても性能向上はなくメモリ使用量のみ倍増するため。スレッド数を4→8に増やすことで、スクレイピングのようなネットワーク待ち主体の処理の同時実行能力は維持した（Render 512MB Instance failed 対策の一環、他に movers集計のSupabase RPC化、O(n)リスト検索のO(1)セット検索化も同時に実施）
  2. 本番実測（`/debug/memory`）で、起動時165MBから検索を重ねると313MBまで単調増加して戻らない現象を調査した結果、Pythonオブジェクトのリークではなく、スレッド並列HTML解析によるglibcのmallocアリーナ断片化がRSS（実メモリ使用量）膨張の原因と特定。加えて `_get_ygores_name_index` にロックがなく、再起動直後の並行リクエストで同じJSONファイルを8〜9本並列ダウンロード＋辞書構築するthundering herd（群衆殺到）状態も確認し、こちらはダブルチェックロック化で別途対処した
- **代替案/経緯**: ワーカー数変更単体では解決せず、後日メモリ内訳エンドポイント（`/debug/memory`、原因特定後に削除）による実測調査を経てMALLOC_ARENA_MAX設定を追加している
- **根拠コミット**: 3ebe885（ワーカー/スレッド数変更）, 60d3239（MALLOC_ARENA_MAX追加・索引ロード排他化）
