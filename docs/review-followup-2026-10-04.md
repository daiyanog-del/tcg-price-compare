# 総合レビューの残項目

## 今回の範囲

- S3: デッキごとの用意済み枚数と不足分の購入候補追加。
- 過去の価格履歴: 読取専用の混入監査。過去データの削除は含めない。
- T4: 本番の待機時間・拒否数を観測可能にし、実測をもとに上限を評価する。

## 所持枚数の方式

全デッキ共通の在庫台帳より変更範囲が小さいデッキ個別方式を採用する。各デッキで使うために用意済みの枚数として扱い、レアリティ別の在庫管理はしない。利点は既存のデッキ作成と不足分購入に直結すること。制約は複数デッキで同じ実物を使い回す在庫配分を管理しないこと。

未入力と0枚を区別する。購入候補の既存枚数を表示して、不足数に達するために必要な追加枚数を確認してから反映する。既存のレアリティ条件は維持する。保存・下書き・同期の契約を拡張し、旧データも読み込めるようにする。DB列や外部依存は追加しない。

## 本番の上限評価

- 店舗検索はプロセス内6実行/待機込み30を維持。画像生成は1実行を維持。
- 検索の受付・共有・拒否・完了・例外、待機/実行時間の件数・合計・最大を固定サイズの集計として保持する。入力名やURLをメトリクスへ記録しない。
- RenderのCPU・メモリ・インスタンス数と同じ時間帯の集計を突き合わせる。API全体のHTTP遅延だけで店舗待機時間を推定しない。
- 累積値は同じプロセス起動単位の差分で集計する。拒否率の母数は受付+共有+上限拒否。待機時間の母数は実際に実行を開始した店舗処理。未完了の仕事は時間集計にまだ含まれない。
- 平均と最大だけでp95を算出しない。最大待機やピークメモリは採取間隔によって過小評価される可能性も記録する。
- 混雑時を含む本番観測が得られるまで上限の最適値とは呼ばない。疑似ベンチは並行性・計測負荷の回帰確認に限定する。

## 接続の状態

開始時、Supabaseコネクターは認証エラー。RenderはMy Workspaceの確認待ち。監査ツールと計測コードの検証を進め、実データ未確認を完了扱いにしない。

## 履歴監査の実行例

```sh
python tools/audit_price_history.py --from 2026-09-01 --to 2026-09-30 --shop カーナベル --summary audit-summary.json --csv audit-candidates.csv
```

日付はJSTで両端を含む。範囲外は未監査。fixture JSONを`--fixture`で指定するとDB接続せず判定を検証できる。通常は既存のSUPABASE_URL/SUPABASE_KEYを環境変数で与える。キーをCLI引数・レポートに記載しない。

販売のcodeは通常品最安値、urlは状態不問最安値に対応し、同一出品を指すとは限らない。買取履歴には元商品URL/型番がなく、通常レアリティの混入は履歴だけでは確定できない。型番不明やOCG形式であることだけでは混入なしを保証できない。

読取は日付単位でページングし、取得件数・重複・途中失敗を確認する。中断時はcomplete=falseと部分結果を出す。RESTでは同時更新に対して完全なスナップショットを保証できない。候補CSVは削除指示ではない。カーナベル買取ステンレスは2026-08-03の保持判断を尊重する。

## 既存の同期表示の制約

既存の端末同期メニューは連携状態を表示し、各変更の送信成功までは表示しない。そのため所持枚数入力時は「この端末に保存しました」とだけ案内する。同期ネットワーク障害の可視化は別の運用改善項目として残す。
